# D-006 — Owned-horse breeding in the normal saved management stable

**Date:** 2026-10-10
**Owner:** GPT integration lead, implementing the owner's request to breed in the actual saved stable while leaving horse visuals and animations alone.

**Scope:** A bounded P2-06 owned-parent pairing flow in **Manage stable**, using the existing canonical horses, public queries, conception transaction, wallet ledger, RNG and atomic save store. External studs, purchases, building upgrades, transfers, renderer changes and `handoff/` are outside this package. This does not claim full P2-06 acceptance.

**Saved pairing:** A read-only plan identifies the saved mare and stallion, their revisions, the fee, due date, unknown ancestry warning and protected future space. Confirming derives the hold again from locked current state and passes it through the existing `ConceptionTransaction.Apply`. One publication saves the child, pregnancy, 50-coin debit, committed reservation and breeding-stream advance together. Exact retries return the original conception; stale, conflicting or ineligible requests cannot roll an outcome or charge. Canceling a preview creates no persistent hold.

**Text-only sandbox boundary:** D-001's prohibition on unapproved coats in player saves gains one explicit, bounded exception for the existing `Sandbox` / `stable-management-prototype` text management save. Its named `stable.text-breeding.v1` policy requires compatible genetics and a complete, supported all-generation genetic closure, but does not assert visual-release support. The default conception path, public presentation resolver and actual renderer retain their existing release requirements. No matrix row, layer, mesh or visual catalog status is promoted. These saved horses may not be sent to the production presenter as approved visual horses. The foaling demo remains separate.

**Timing and ancestry:** The new policy preserves the prototype's four-day pregnancy, three-day foal and three-day youngster stages, adulthood at birth +6 and breeding eligibility at birth +8. Mare recovery ends at birth +2. The relatedness block threshold remains 1/8 as a game rule. Recorded family links supply a conservative minimum relatedness, so parent–child and sibling pairings remain blocked even when earlier ancestry is unknown. Unknown ancestry is explicitly allowed with a warning; immutable parentage is not rewritten into fictitious unrelated founders. The lifecycle service recognizes this exact timing policy alongside historical `cozy.policy.v1` conceptions.

**Conservative space:** This small prototype supports four protected eventual home allocations. Every owned canonical horse, including an unborn or growing child and any horse temporarily away, consumes one allocation; unrelated pending holds consume one each. A committed child's historical hold is not counted again. The proposed child needs one remaining allocation. Four stage windows carry this conservative bound through adulthood. This is future housing protection, not a claim that a nursing foal already occupies an adult stall. Unknown projects, homes or capacity evidence block rather than inventing additional space. Facility expansion remains later work.

**Starter compatibility:** Fresh normal stables create mature Juniper (mare) and Maple (stallion). Existing normal saves receive a locked, one-time upgrade only for the exact original prototype starter pair, identified by origin, owner, metadata and the appearance seeds derived by the original bootstrap. Renamed names remain intact. The upgrade changes eligibility roles and their mature age baseline, records its marker and preserves IDs, genome, appearance seeds, parentage, wallet, care, calendar and all RNG streams. It never invents a birth date or replaces the stable. Ambiguous or unrelated horses are not rewritten. Generic save protections remain intact; no wire/schema change is planned.

**Acceptance:** Prove normal save → read-only/canceled plan → committed pairing → reload → birth → naming → growth with the same child and one fee/RNG advance. Cover real-file interrupted publication, exact retry/conflict, stale state, funds, roles, age/recovery, overbooking, legacy starter upgrade and strict default visual gates. Build and run the actual Godot management flow; preserve all frozen horse assets and matrix hashes. Record verified results in `STATUS.md`, then commit and push only the existing pilot branch.
